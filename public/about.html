About EvidenceGuard

Engineering specification, cryptographic architecture, forensic custody workflows, and transparent system limitations.

⚠️

The Problem

Digital evidence is fundamentally intangible and vulnerable: electronic files can be trivially copied, modified, swapped, or deleted without leaving obvious physical traces. In courtrooms, a broken or unverifiable chain of custody risks evidence dismissal and failed prosecutions. Traditional relational databases are susceptible to privileged insider manipulation or unauthorized file replacement on server storage.

🛡️

The Solution

EvidenceGuard pairs SHA-256 cryptographic hashing with a secure database, an automated verification engine, an immutable hash-linked block ledger, and a cryptographically linked append-only audit trail. Any alteration of a registered digital artifact—even a single bit in a gigabyte video—mathematically diverges from the recorded block hash, enabling instant, irrefutable tamper detection.

Project Objectives

✔

✔

Custody & Verification Workflow

1

Authentication & RBAC Enforcement

Operators authenticate using salted bcrypt credentials. The server sets an HTTP-only JWT cookie. Each API request passes through role verification.

2

Evidence Upload & Server-Side Hashing

The investigator submits a file and metadata. The server streams the payload to compute the authoritative SHA-256 digest and verifies it against any optional client hash.

3

Storage & Block Sealing

The binary is saved to protected disk storage using an opaque UUID storage key. The metadata and hash are appended into a new block linked to the latest ledger block.

4

Cryptographic Audit Event Ingestion

Events are logged with user ID, action, timestamp, IP, and previous audit entry hash, guaranteeing that the log trail cannot be truncated or retroactively edited.

5

Forensic Verification

During court proceedings, an analyst submits the evidence file. The system computes its current hash, performs timing-safe buffer comparison against the block ledger, and returns a verified or tampered verdict.

⚠️ Transparent System Limitations

In keeping with academic integrity and rigorous cybersecurity principles, EvidenceGuard explicitly acknowledges the following design and architectural boundaries:

  • Centralized Ledger Storage: The ledger blocks and audit logs live in the same MongoDB instance as operational records. It is a single-node prototype, not a decentralized distributed consensus network.
  • Database Administrator Compromise: A database administrator with root access who selectively recomputes downstream SHA-256 hashes could theoretically rewrite both the block chain and the audit chain.
  • Origin Authenticity vs. Integrity: SHA-256 hashes prove that a file matches what was registered at intake. They do NOT prove that the file was authentic when initially gathered in the physical world, nor do they prove who originally created it.
  • Standard Server Storage: Digital files are stored on server disk storage, not inside a certified Hardware Security Module (HSM) or hardware-enforced Write Once Read Many (WORM) storage appliance.
  • No Automated Password Reset Flow: Password reset currently requires administrative database intervention; there is no automated email-based or self-service password recovery flow implemented in this prototype.
  • Sequential Case ID Guessability: The public QR verification endpoint uses sequential Case IDs (EG-YYYY-NNNN), which could be sequentially enumerated without external rate limiting or random GUID identifiers.
